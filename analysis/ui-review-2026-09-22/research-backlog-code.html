Directly relevant interaction findings

ID Source-derived gesture/state and verified usage Human effect Relevance to Switchflow and novelty Caveat / recommendation
B01 With hideEmptyColumns, Backlog.md reveals otherwise hidden empty status columns after drag start using a zero-delay timer; it resets them on drag end. Board.tsx:541-580 explains the browser constraint: synchronously changing the layout during native dragstart can abort the drag. TaskCard invokes this through TaskColumn's onDragStart path (TaskCard.tsx:88-128, TaskColumn.tsx:392-400). A person may normally hide unused stages without losing the ability to drop a card into one. The target becomes visible once the drag is safely established. New, high-value implementation detail. Switchflow's inspected board intends hidden targets to reappear while dragging, but its dragstart state does not render again, so that intent can fail. Adopt the behaviour, not its component structure: schedule target revelation after dragstart, give it a visual/status announcement, and restore the prior compact view after drop/cancel. Test a drag to an initially empty hidden status at desktop and touch/pointer alternatives.
B02 Reorder position is not guessed from the card alone. Hovering the top or bottom half sets before/after, renders a blue insertion marker, and drop converts that marker to an ordered-ID request. A hover on the lifted card is an explicit no-op. TaskColumn.tsx:151-210, TaskColumn.tsx:323-411. The board passes the resulting reorder into the app's surgical task-store update rather than remounting the whole board (Board.tsx:424-435, App.tsx:724-732). The user sees exactly where a single task will land and can lift/drop in place without an accidental move to the end. A successful move does not reset the rest of the workset. New. It directly addresses the local finding that Switchflow drops before a hovered card with no edge cue or marker. It makes visual task order legible without claiming that order is an approved delivery sequence. Add explicit top/bottom markers and an unchanged-order guard. Keep this as board ordering only: an order change must not alter initiative/milestone approval or the proposed Next decision.
B03 Selection is treated as a visible set, not latent bulk state. Ctrl/Cmd toggles, Shift adds a range, and Escape clears. When filtering or collapsing hides a task, the selection is pruned before a batch action; cross-branch records are excluded from selection ranges. Board.tsx:311-345, Board.tsx:615-635, TaskColumn.tsx:370-389. The rendered selection toolbar exposes count, target status and Clear (Board.tsx:675-711). A filter change cannot silently move cards the person can no longer see. A multiple-card move has a visible count and explicit target. New. This is a useful contract if Switchflow adds multiselect, or when a future sidebar/Next panel changes the visible workset during an action. Reuse the visibility rule and count/target confirmation. Do not copy batch lifecycle moves until authorization semantics are designed: a batch status change can carry materially different approval consequences in Switchflow.
B04 A batch dragged across columns deliberately appends in the target lane; it keeps the source board reading order rather than click order. A same-target batch move is a no-op and preserves selection. Per-task failures are surfaced with IDs/reasons while changed records update in place. Board.tsx:348-408; TaskColumn intentionally suppresses a misleading per-card insertion marker for batch drags (TaskColumn.tsx:161-167, TaskColumn.tsx:329-334). The outcome is predictable and partial failure is explainable instead of appearing as an unexplained partial board refresh. New positive pattern, especially relevant to agent/human co-ordination. If batch movement arrives, state "moved X of Y" with named exceptions, preserve the source ordering, and make the target insertion rule visible. Never offer an undo that would overwrite a concurrent agent edit; provide a new deliberate operation/readback instead.
B05 Cross-branch data is visibly readable but non-movable: card drag is disabled, the board supplies a temporary explanation naming the required branch, range selection skips it, and the detail modal displays a read-only notice and disables mutations. TaskCard.tsx:81-128, TaskCard.tsx:179-241, TaskDetailsModal.tsx:1211-1219. These components are live: App supplies tasks to BoardPage and TaskList (App.tsx:937-973). The system explains why a visible record is not actionable at the attempted action, rather than hiding it or failing afterward. New. Switchflow similarly fences editing while agents are active/queued and distinguishes foreign/completed records, but its UI should standardize the reason-at-control pattern across task, initiative, milestone and agent action controls. Import the presentation rule: show read-only/queued/agent-fence reason adjacent to disabled controls and retain read access. Do not expose a branch switch control unless Switchflow's governance model permits that action.
B06 Board lane, filters and selected milestone are URL-backed; lane mode is also stored locally. A deep link may highlight/open a card, then removes the one-shot highlight parameter. BoardPage.tsx:51-106, BoardPage.tsx:109-189. The sidebar preserves the originating board query when opening a task (SideNavigation.tsx:537-563); App invalidates malformed task links with a focusable dismissible alert (App.tsx:734-756, App.tsx:1054-1069). A search result or shared link opens one record without throwing away the source workset. Broken/ambiguous links explain the recovery path. New. The report recommends filter persistence, but this gives a concrete reversible-history contract. It would fix the common detail-close problem after global search or Next-panel navigation. Preserve project + source route + filter state on open. Make any task/initiative URL precise enough to recover context; invalid or stale identifiers should return to the originating workset with a clear, focusable message.
B07 Detail reads are guarded against stale asynchronous responses: each modal read binds a session, ID and data-generation; a later response can only fill the currently awaited modal. An unsuccessful refresh leaves an already-visible detail intact. App.tsx:734-802. The modal separately asks before closing or following a link with unsaved edits (TaskDetailsModal.tsx:646-705); the shared modal traps focus, restores the prior focus, locks only body scrolling, and keeps its header sticky (Modal.tsx:45-104, Modal.tsx:109-142). Rapid search/navigation/refresh does not replace the record a person is editing with a late response. Keyboard users return to their origin after close. New detail beneath the existing report's broader "read-first modal" recommendation. It is particularly important with Switchflow's cross-project selection and periodic agent updates. Treat record identity + project + refresh generation as one UI state key. Preserve current content through non-terminal refresh failures, confirm leaving dirty fields, and return focus to the source trigger.
B08 Destructive state transitions explicitly distinguish failure after movement from failure before/unknown movement. Demotion refreshes and asks the user to inspect drafts/dependents instead of submitting the same request again; archiving behaves similarly. api.ts:38-71, TaskDetailsModal.tsx:1018-1107, App.tsx:891-913. A connection error cannot encourage an accidental second archive/demotion. The person sees a bounded investigation next step. New. It fits Switchflow's evidence-preserving recovery model and is more important than a generic toast/undo for stateful governance records. Use result-state messages such as "applied; refresh failed" or "outcome unknown; inspect before retry." Keep any destructive confirmation specific about the move and downstream records affected.
B09 Backlog.md uses field-specific disclosure, not one empty-field rule. In read mode, Description, Plan and Notes always retain their headings and show “No …”; each becomes a large editor only after the global Edit action (TaskDetailsModal.tsx:1124-1201, TaskDetailsModal.tsx:1278-1300, TaskDetailsModal.tsx:1599-1645). Final Summary has the explicit predicate `mode !== "preview" finalSummary.trim().length > 0, so an absent value is omitted from read view but is offered in edit mode ([TaskDetailsModal.tsx:1700-1723](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1700-L1723)). Parent and subtask regions are derived from availableTasks and render only when a relation resolves; they link to existing records and contain no Add-subtask path ([TaskDetailsModal.tsx:433-447](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L433-L447), [TaskDetailsModal.tsx:1224-1260](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1224-L1260), [TaskDetailsModal.tsx:1302-1351](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1302-L1351)). Conversely, References shows “No references” plus a preview-mode Add form for an editable task, Dependencies always exposes an inline chip/input control, and persisted tasks always show Comments with a count/“No comments”; the comment composer requires edit mode and local write access ([TaskDetailsModal.tsx:1353-1425](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1353-L1425), [TaskDetailsModal.tsx:1647-1698](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1647-L1698), [TaskDetailsModal.tsx:1905-1927](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/TaskDetailsModal.tsx#L1905-L1927), [DependencyInput.tsx:55-226](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/components/DependencyInput.tsx#L55-L226)). App supplies the full task corpus and navigation callback, so these hierarchy conditions are live component inputs, not dead presentation code ([App.tsx:1072-1093`](https://github.com/MrLesk/Backlog.md/blob/9a9fe226d5889b75778208c39ff72a7214876b4a/src/web/App.tsx#L1072-L1093)). A reader is not confronted with blank editors for optional prose, but can still distinguish a known-empty description/comment/reference from an absent completion summary or relationship. The available Add path signals whether the empty state is actionable; cross-branch access removes that path and has an explicit read-only reason.

Useful, but do not import unchanged

Candidate Source fact Why not to copy verbatim
Browser search as the only global queue Sidebar search is debounced 200 ms, fetches up to 15 and displays the first 5 results. SideNavigation.tsx:388-447 It is a locator, not a "Needs you" priority surface. Switchflow's Next panel needs explicit human-gate ranking and must not hide the sixth valid match without an all-results route.
Column sort menu Priority/creation-date sorting is a no-drag alternative when every card is local and more than one card exists. TaskColumn.tsx:107-135, TaskColumn.tsx:261-319 A sorting menu changes visual/card order, which Switchflow must not let masquerade as approved phase or milestone order. It also does not supply individual keyboard before/after placement; define a separate accessible move control if manual ordering is needed.
Generic modal scrolling The shared modal caps itself at 94vh and gives the whole detail one overflow-y-auto scroll container. Modal.tsx:109-142 It is better than a page-height overlay but does not solve Switchflow's long-history requirement. Retain one main reader scroll; bound only independently navigable/history lists with visible older-record access.
Saving every optional narrative field Backlog.md's task save sends Description, Plan, Notes and Final Summary even when currently blank. TaskDetailsModal.tsx:801-856 This is not a presence/discoverability model. Switchflow should avoid showing a blank block reason, plan, notes or final-summary editor in its default read view; it should only clear a known existing value after a clear action/save, consistent with revision protection.
Client workset without browser paging The task list updates filters and count but maps the resulting displayTasks table in full. TaskList.tsx:376-432, TaskList.tsx:808-861 It reinforces the main report's conclusion: Backlog.md is not a ready-made answer to Switchflow's large-history/list paging. Offer older records only where volume warrants it—through an explicit bounded window, Load older, or a cursor-backed history endpoint—and label what is currently shown and, where cheaply available, the total.

Review boundary and next validation

These are source-backed interaction candidates, not a request to restore Backlog.md's native UI. The Switchflow custom product should retain owner approvals, run admission and recovery policy while borrowing the narrowly useful contracts above. Before a change, render a disposable Switchflow fixture that contains hidden empty statuses, 30+ tasks, active filters, cross-project/foreign records, a concurrent refresh, and a deliberately interrupted move. Verify pointer, keyboard, focus-return and narrow viewport behaviour against that fixture.
