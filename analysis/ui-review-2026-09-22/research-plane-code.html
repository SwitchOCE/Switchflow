Plane Community Edition code review: human interaction appendix

Scope and evidence boundary

This is a static review prepared 22 September 2026, of the public Plane Community Edition source pinned to v1.4.0 / 917b23a6c16d93fc00cef67900eff2755e8b13f7 (release dated 31 July 2026). The pin is a reproducible review target, not a claim that it is the current Plane release. I unpacked that tag locally and traced rendered callers and handlers. No Plane instance was run, no API failure was injected, and no assistive technology test was performed. Consequently every result below is source-derived, not runtime-verified; hosted/paid edition behaviour may differ.

KanBanLayout is a live project route wrapper for BaseKanBanRoot, including the project-role edit predicate (caller). This is why the Kanban observations below are not claims about an unreferenced component.

Source-traced findings

The transfer statements are candidate proposals only. The consolidated Switchflow report decides priority, scope, and acceptance criteria across all comparators.

# Gesture or state traced Human effect Switchflow relevance and novelty against the existing Plane docs review
P-C01 The active Kanban root requests grouped initial results at 30 per group, or 10 when subgrouping, then calls a group/subgroup next-page action when that group is not already paginating (root). A group computes whether more are available and supplies either a sticky Load more control for subgroups or an intersection-observer sentinel and loaders for ordinary columns (group). A large board is progressively disclosed per column rather than becoming one long, unbounded document. The explicit subgroup affordance also gives an intentional alternative to scroll-triggered loading. Candidate: for high-volume board columns, use a visible item/count model with incremental access, a visible “load more” fallback, and localized scroll. This is new code evidence for the report’s history/scroll concern; it proves grouped-board paging only, not activity paging. Caveat: Plane implements the visible control as a click-only div with explicit a11y-lint suppression (lines 261-270); Switchflow should use a real button.
P-C02 Kanban maps each configured column even where its issue-id array is empty; it only omits one if the saved visibility decision says showGroup === false (columns). Each rendered group has a min-h-[120px] column drop target (target, surface). The separate list layout can hide a zero-count group when showEmptyGroup is false (predicate). Empty workflow destinations remain discoverable and droppable in Kanban, while a user-controlled/format-specific “hide empties” rule can reduce list noise. Candidate: never hide a valid destination while a drag is active; reserve a stable, appropriately sized empty drop area and make any compacting preference explicit. Plane’s 120px is one implementation example, not a standard. This directly contrasts with Switchflow’s observed hidden-empty-target failure (F32). New source detail: visibility is a saved group decision, not merely a count test.
P-C03 Dragging onto a column changes the column surface, supports column and board autoscroll, blocks prohibited workflow drops with a warning toast, and only calls the drop handler if valid (column handler; board autoscroll). Dropping onto the trash target opens a confirmation modal rather than deleting immediately (delete target). The user can see the intended destination, reach it on a wide board, receives a reason for an invalid state transition, and gets a deliberate destructive-action checkpoint. Candidate: add target highlight, autoscroll, an insertion cue, and a failure message that names the constraint; require confirmation for destructive drops. New code corroboration beyond the existing docs review. Do not copy Plane’s temporary top-centre delete zone verbatim; Switchflow needs a persistent, labelled, keyboard-accessible delete path too.
P-C04 A card is both draggable and a drop target. It refuses self-drops and displays DropIndicator on hover (card). The drop payload extracts whether the hitbox means “reorder below”; sort order then calculates top, bottom, between, and empty-column positions (payload and order). The handler applies group/subgroup and order changes and routes the result to update actions, with an error toast on rejection (update path). Reordering has a legible above/below outcome instead of “always before the hovered card”; an action failure is surfaced. A successful cross-column drop is highlighted, and non-manual ordering also scrolls it into view (highlight). Candidate: calculate above/below from the pointer, display the insertion point, reject self-drops, and surface persistence failure. This is a direct improvement path for Switchflow F33’s ambiguous always-before outcome. Static limit: this trace proves an error toast, not an optimistic rollback or undo; failure recovery needs its own Switchflow design and test.
P-C05 Card dragging is allowed only for supported groupings, non-temporary items, and roles that can edit; an attempted native drag otherwise produces a specific warning (guard). Far columns are lazy-mounted: only the first five groups / two subgroups are rendered by default, with a placeholder until visible (lazy boundary). Plane avoids silently accepting impossible moves and limits initial visual work on broad boards. The latter can make an offscreen column temporarily a placeholder rather than an immediately available precise target. Candidate: make a move’s availability and reason explicit before/during drag; use lazy rendering only with an accessible, predictable navigation alternative and test long-board drag reachability. New caveat absent from the docs comparison.
P-C06 The peek route closes on Escape and restores focus to issue-{id}, but only when no modal, editor dropbar, image fullscreen view, or focused INPUT blocks the shortcut; outside-click close has similar guards (peek guards). A person returning from a task view lands back on the exact card rather than losing board context, while common nested overlays are protected from an accidental close. Candidate: record opener element and restore focus; scope Escape/outside-close to the active layer; suppress close while the editor has its own UI. This adds code proof to the existing detail-view recommendation. Caveat: source inspection cannot establish how this behaves with every rich-editor focus state, so verify with keyboard and screen-reader UAT.
P-C07 The same peek has three layouts: half-width side peek, 5/6 modal, and full screen. Side/modal put details, properties, and activity into one vertical content scroller; full screen separates a main scroll region from a fixed 400px properties rail (layouts, scroll regions). Users can expand when a task description needs room, and the full-screen mode reduces unnecessary traversal between reading/editing and task properties. It does not eliminate long activity scrolling in the side/modal modes. Candidate: provide a generous resize/full-screen detail view and separated detail/property regions for dense work. Do not adopt Plane’s fixed pixel widths or assume mode switching alone fixes histories: provide bounded history access when volume warrants it, and preserve scroll context. This sharpens the prior “modal sizing” finding with an implementation caveat.
P-C08 The route derives a read-only state from ADMIN/MEMBER project permissions (permission). Detail returns nothing if the issue/project is absent, renders parent only when present, disables title/description while read-only or archived, and omits the description-version UI entirely for disabled users (conditionals). The outer view instead displays a recoverable error screen when the fetch itself errors (error branch). State-specific UI avoids inviting edits a viewer cannot make, but an absent cached entity can be an unexplained blank in this component path; a disabled reviewer also loses this description-version entry point. Candidate: distinguish “loading”, “missing/deleted”, “no permission”, and “read-only” visibly; preserve useful read/audit affordances where policy permits. New conditional-rendering evidence. Do not copy blank returns for absence.
P-C09 Activity filter/sort choices are stored under local-storage keys, a filter dot signals a non-default selection, and the component prevents removing the last active filter (activity controls, indicator). The activity store appends results newer than the latest known activity using created_at__gt; the reviewed activity component has no “load older” control or cursor/page state (store, render). Filtering and sort preference survive moving between tasks, and an active filter is not invisible. However, this client trace does not show historic activity pagination; it is only an incremental-newer-event fetch. Candidate: make non-default history filters visibly persistent and prevent an empty “no types selected” state. For Switchflow, add deliberate, volume-appropriate access to older history; do not cite Plane as proof that activity history is paginated. New source boundary requested for this report.
P-C10 Description edits debounce for 1.5s, save again on unmount if dirty, and use an unload-warning hook while submission is active (editor, warning state). Along this peek path, the update wrapper catches a rejected update and shows a toast rather than rethrowing (wrapper). The intended interaction is low-interruption autosave with leave protection. Static control flow suggests a failed description update can show a toast yet still allow the editor’s fulfilled caller/finally path to clear its dirty/submitting state. Candidate: keep an explicit dirty/saving/saved/error state and a retry action until the server confirms the exact content; warn before navigation while dirty. Treat Plane’s possible “toast but no retained retry state” as a test hypothesis, not a runtime defect, until a forced-failure run confirms it. This is new resilience evidence.

Recommendations to carry forward

  1. Convert Switchflow’s top navigation to an accessible sidebar that preserves the current board/task context, then restore focus to the opener when a detail view closes (P-C06).
  2. Make the next actionable milestone/task visible as a dedicated, explainable callout; do not make people infer it from column position alone. Plane’s code supports orientation and safe transitions but does not itself solve prioritisation.
  3. Keep empty columns as stable, appropriately sized, visibly highlighted drag targets during a drag; apply hide-empty only outside a drag and label the setting. Plane’s 120px minimum is an example, not a universal target (P-C02).
  4. Replace the current always-before drop rule with above/below insertion feedback, target autoscroll, visible invalid-move reasons, and a post-drop highlight (P-C03–05).
  5. Give task detail a resizable/full-screen reading mode, separated properties where space permits, and return the person to the originating card on close (P-C06–07).
  6. Bound board and history rendering independently when volume warrants it: use incremental board access with a semantic “load more” button, and provide a deliberate route to older activity rather than relying on one page scroll (P-C01, P-C09).
  7. Model absence, permission, archive, loading, saving, saved, and save-failed as visibly distinct states; retain retry/dirty state after any failed write (P-C08, P-C10).
  8. Provide a keyboard-equivalent move/reorder path and semantic controls for every action. Plane’s reviewed group loader and filter option use click-only divs; copying them would carry an accessibility regression (P-C01, P-C09).

Candidates deliberately not imported

  • Plane’s fixed half-width, 5/6, and 400px values are layout choices, not standards; Switchflow needs responsive sizing against its actual content and viewport.
  • Auto-load-on-scroll is not sufficient by itself: preserve a visible button and an item/result count so people know more history exists.
  • A transient drag-to-delete target should not be the only deletion affordance, and deleting needs a confirmation plus a recovery story.
  • The source does not prove an undo or rollback after failed drag persistence. Do not describe Plane as having one and do not use its error toast as a substitute.
